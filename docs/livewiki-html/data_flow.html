Data Flow

How data moves through the UserStore system

Overview

UserStore follows a clear data flow pattern from application code through the store layer to the database and back. This document explains the lifecycle of user data operations.

User Creation Flow

Creating a New User

Step-by-Step Process

  1. Application calls NewUser()
    • Creates a new userImplementation instance
    • Generates a unique short ID
    • Sets default values (status: unverified, role: user)
    • Initializes timestamps (created_at, updated_at)
    • Sets soft_deleted_at to MAX_DATETIME
  2. Application sets user properties
    • Uses method chaining: SetEmail(), SetFirstName(), etc.
    • Optionally calls SetPasswordAndHash() for password hashing
    • Can set metadata via SetMeta() or SetMetas()
  3. Application calls UserCreate()
    • Store validates the user data
    • Generates INSERT SQL statement
    • Executes SQL against database
    • Returns error if operation fails
  4. Database stores the record
    • Record is persisted with all fields
    • Metadata is stored as JSON string
    • Password is stored as bcrypt hash

User Retrieval Flow

Finding Users

FindByID Flow

  1. Application calls UserFindByID()
    • Store generates SELECT SQL with WHERE id = ?
    • Excludes soft-deleted records by default
  2. Database executes query
    • Returns matching record or nil
  3. Store hydrates user object
    • Creates userImplementation from database row
    • Parses JSON metadata into map
    • Returns UserInterface to application

UserList Flow (with Query Builder)

  1. Application builds query
    • Calls NewUserQuery()
    • Chains filter methods: SetStatus(), SetEmailLike(), etc.
    • Sets pagination: SetLimit(), SetOffset()
    • Sets sorting: SetOrderBy(), SetSortDirection()
  2. Application calls UserList()
    • Store validates query parameters
    • Generates SELECT SQL with WHERE, ORDER BY, LIMIT, OFFSET
    • Applies soft delete filter unless explicitly included
  3. Database executes query
    • Returns matching rows
  4. Store hydrates user objects
    • Creates slice of UserInterface from rows
    • Returns slice to application

User Update Flow

Updating Users
  1. Application retrieves user
    • Calls UserFindByID() or UserList()
  2. Application modifies properties
    • Calls setter methods: SetEmail(), SetFirstName(), etc.
    • DataObject tracks changed fields
  3. Application calls UserUpdate()
    • Store generates UPDATE SQL with changed fields only
    • Updates updated_at timestamp
    • Executes SQL against database
  4. Database updates record
    • Only changed fields are updated
    • Metadata is re-serialized as JSON

Soft Delete Flow

Soft Deleting Users
  1. Application calls UserSoftDelete()
    • Store generates UPDATE SQL for soft_deleted_at
    • Sets soft_deleted_at to current timestamp
  2. Database updates record
    • Record remains in database
    • soft_deleted_at is set to deletion time
  3. Subsequent queries exclude record
    • Default queries filter WHERE soft_deleted_at > NOW()
    • Record appears deleted to application

Password Flow

Password Operations

Password Storage

  1. Application calls SetPasswordAndHash()
    • Uses bcrypt to hash the password
    • Stores the hash in the password field
    • Plain text password is never stored

Password Verification

  1. Application calls PasswordCompare()
    • Retrieves stored hash from user object
    • Uses bcrypt to compare input password with hash
    • Returns true if match, false otherwise

Metadata Flow

Metadata Operations

Setting Metadata

  1. Application calls SetMeta() or SetMetas()
    • SetMeta() - upserts single key-value pair
    • SetMetas() - replaces entire metadata map
    • UpsertMetas() - merges with existing metadata
  2. Metadata is serialized
    • Map is converted to JSON string
    • Stored in metas column

Retrieving Metadata

  1. Application calls GetMeta() or GetMetas()
    • GetMeta() - retrieves single value by key
    • GetMetas() - retrieves entire map
  2. JSON is deserialized
    • JSON string is parsed back to map
    • Returns value or map to application

Migration Flow

Database Migrations

MigrateUp (Table Creation)

  1. Application calls MigrateUp()
    • Store generates CREATE TABLE SQL
    • Uses SQL builder for database-agnostic syntax
    • Includes all columns with proper types
  2. Database executes SQL
    • Table is created if not exists
    • Supports transaction mode via optional tx parameter

MigrateDown (Table Drop)

  1. Application calls MigrateDown()
    • Store generates DROP TABLE SQL
  2. Database executes SQL
    • Table is dropped
    • All data is permanently lost

Transaction Support

Migration methods support optional transaction parameter:

// With transaction
tx, _ := db.Begin()
err := store.MigrateUp(ctx, tx)
if err != nil {
    tx.Rollback()
    return err
}
tx.Commit()

Data Validation

UserStore performs validation at multiple layers:

  • Query validation - UserQueryInterface.Validate() checks query parameters
  • Store validation - Checks required fields before database operations
  • Database constraints - Database enforces data types and constraints

Error Handling

Errors are propagated through the call stack:

  • Database errors are returned as-is
  • Validation errors include descriptive messages
  • Application should handle errors appropriately
