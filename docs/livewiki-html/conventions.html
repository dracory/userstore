Conventions

Coding and documentation conventions for UserStore contributors

Naming Conventions

Method Naming

Rule: Use consistent prefixes for different types of methods

Getters

  • Use Get prefix for getter methods
  • Examples: GetID(), GetName(), GetEmail(), GetStatus()

Setters

  • Use Set prefix for setter methods
  • Examples: SetID(), SetName(), SetEmail(), SetStatus()
  • Setters should return the interface for method chaining

Boolean Checks

  • Use Is prefix for boolean check methods
  • Examples: IsActive(), IsInactive(), IsAdministrator()

Has Methods

  • Use Has prefix for methods checking if a property is set
  • Examples: HasEmail(), HasLimit(), HasStatus()

Variable Naming

  • Use camelCase for local variables and function parameters
  • Use PascalCase for exported types and functions
  • Use camelCase for private types and functions

Constant Naming

  • Use UPPER_SNAKE_CASE for constants
  • Group related constants with common prefixes
  • Examples: USER_STATUS_ACTIVE, COLUMN_EMAIL, ERROR_EMPTY_STRING

Interface Naming

  • Use PascalCase with Interface suffix
  • Examples: StoreInterface, UserInterface, RoleInterface

Implementation Naming

  • Use camelCase with Implementation suffix
  • Examples: storeImplementation, userImplementation, roleImplementation

Code Structure

File Organization

  • One major component per file
  • Test files should be named *_test.go
  • Group related constants in consts.go
  • Group utility functions in functions.go

Interface Definition

  • Define interfaces in interfaces.go
  • Include all public methods in the interface
  • Use descriptive method names
  • Include comments for complex methods

Implementation

  • Implement interfaces in separate files
  • Use struct embedding for base functionality
  • Include compile-time interface verification

Method Chaining

Setter Return Values

  • Setters should return the interface type
  • This enables fluent method chaining
// Correct
func (o *userImplementation) SetEmail(email string) UserInterface {
    o.Set(COLUMN_EMAIL, email)
    return o
}

// Incorrect
func (o *userImplementation) SetEmail(email string) {
    o.Set(COLUMN_EMAIL, email)
}

Error Handling

Error Returns

  • Always return errors from functions that can fail
  • Return errors as the last return value
  • Use descriptive error messages

Error Wrapping

  • Wrap errors with context when appropriate
  • Use errors.Join() for combining errors
  • Include context about what operation failed
return errors.Join(errors.New("userstore.NewStore"), err)

Documentation

Code Comments

  • Add comments for exported functions
  • Document complex logic
  • Keep comments up to date
  • Use proper Go documentation format

Function Documentation

// FunctionName does something useful.
//
// Parameters:
//   - param1: Description of parameter 1
//   - param2: Description of parameter 2
//
// Returns:
//   - Type1: Description of return value 1
//   - error: Error if operation fails
func FunctionName(param1 Type1, param2 Type2) (Type1, error) {
    // Implementation
}

LiveWiki Documentation

  • Update LiveWiki for new features
  • Add examples to getting started guide
  • Update API reference for new methods
  • Include metadata header in all pages

Testing

Test Structure

  • Write tests for all public functions
  • Use table-driven tests for multiple test cases
  • Test both success and error paths
  • Aim for high code coverage

Test Naming

  • Use TestFunctionName format
  • Use descriptive test case names in table-driven tests

Mocking

  • Mock external dependencies (database, etc.)
  • Use interfaces for easy mocking
  • Keep tests fast and isolated

Database Operations

SQL Generation

  • Use SQL builder for database-agnostic queries
  • Don't write raw SQL strings
  • Let the builder handle database-specific syntax

Transaction Support

  • Support optional transaction parameter
  • Use variadic parameter for transaction
  • Example: func (ctx context.Context, tx ...*sql.Tx) error

Security

Password Handling

  • Never store plain-text passwords
  • Always use bcrypt for hashing
  • Provide SetPasswordAndHash() for automatic hashing
  • Provide PasswordCompare() for secure comparison

Input Validation

  • Validate all user inputs
  • Use query builder to prevent SQL injection
  • Sanitize data before storage

Performance

Database Queries

  • Use pagination for large result sets
  • Select only needed columns
  • Use indexes on frequently queried columns
  • Avoid N+1 query problems

Memory Management

  • Close database connections when done
  • Limit result sets with pagination
  • Reuse objects where possible

Git Conventions

Commit Messages

  • Use clear, descriptive commit messages
  • Use imperative mood: "Add feature" not "Added feature"
  • Keep commits focused on a single change

Branch Naming

  • Use feature/feature-name for features
  • Use fix/bug-description for bug fixes
  • Use docs/documentation-update for documentation

Code Review

Review Checklist

  • Code follows naming conventions
  • Code is properly documented
  • Tests are included and passing
  • Error handling is correct
  • Security best practices are followed
  • Performance considerations are addressed

Best Practices

General

  • Keep functions small and focused
  • Use meaningful variable names
  • Avoid code duplication
  • Write self-documenting code
  • Keep the codebase clean and organized

Go Specific

  • Use gofmt for code formatting
  • Use golint for linting
  • Follow Go best practices
  • Use idiomatic Go code
